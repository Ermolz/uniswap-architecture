# Технічний огляд Uniswap V2, V3 та V4: архітектура, callbacks і узгодженість стану

Мета огляду — простежити, як контракт передає керування зовнішньому коду, допускає проміжний борг і перевіряє завершений розрахунок. Центральне питання полягає у відмінності між станом, доступним під час callback, та умовами успішного повернення операції. Аналіз охоплює ядра протоколів; поведінка конкретного маршрутизатора чи hook потребує окремої перевірки.

Використано незмінні зрізи офіційних репозиторіїв: [V2 — 6a9e7c97860676e0992f22a49665760444c1cdf5](https://github.com/Uniswap/v2-core/tree/6a9e7c97860676e0992f22a49665760444c1cdf5), [V3 — 5ea68a77cb541c6b3812df783be71ba8c081e25f](https://github.com/Uniswap/v3-core/tree/5ea68a77cb541c6b3812df783be71ba8c081e25f), [V4 — bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6](https://github.com/Uniswap/v4-core/tree/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6). Посилання біля фрагментів фіксують файл, commit і рядки. Після кожного фрагмента наведено окремі пояснення, які не є частиною оригінального коду. Висновки стосуються цих джерел і не засвідчують відповідність будь-якому розгорнутому байткоду.

## 1. V2: резерви пари та оптимістична передача

Контракт `UniswapV2Pair` зберігає адреси двох токенів, резерви та часові акумулятори. Резерви — зафіксований обліковий стан; фактичні ERC-20 баланси читаються окремо. Ці величини можуть тимчасово відрізнятися через попередню оплату, передачу виходу чи callback. Тому огляд `swap` має перевіряти всю послідовність, а не лише формулу добутку.

### 1.1. Межа повторного входу та зовнішній переказ

[UniswapV2Pair.sol, L31–L35](https://github.com/Uniswap/v2-core/blob/6a9e7c97860676e0992f22a49665760444c1cdf5/contracts/UniswapV2Pair.sol#L31-L35)
```solidity
    modifier lock() {
        require(unlocked == 1, 'UniswapV2: LOCKED');
        unlocked = 0;
        _;
        unlocked = 1;
```

- L31 — // Модифікатор визначає спільний бар’єр для операцій із резервами пари.
- L32 — // Повторний вхід у захищену операцію завершується помилкою LOCKED.
- L33 — // Перед виконанням тіла функції прапорець блокує наступний захищений виклик.
- L34 — // У цій точці виконується тіло функції з активним блокуванням.
- L35 — // Після успішного завершення тіла доступ до захищених операцій відновлюється.

Блокування застосовано до `swap`, `mint`, `burn`, `skim` і `sync`. Воно не забороняє зовнішні виклики як такі та не перетворює всі читання стану на завершений розрахунок. Зокрема, getter резервів доступний під час callback і показує попередні резерви до їх оновлення. Отже, сторонній контракт повинен розуміти часову точку такого читання.

[UniswapV2Pair.sol, L44–L47](https://github.com/Uniswap/v2-core/blob/6a9e7c97860676e0992f22a49665760444c1cdf5/contracts/UniswapV2Pair.sol#L44-L47)
```solidity
    function _safeTransfer(address token, address to, uint value) private {
        (bool success, bytes memory data) = token.call(abi.encodeWithSelector(SELECTOR, to, value));
        require(success && (data.length == 0 || abi.decode(data, (bool))), 'UniswapV2: TRANSFER_FAILED');
    }
```

- L44 — // Приватна функція виконує переказ заданого токена конкретному одержувачу.
- L45 — // Низькорівневий виклик передає керування токену через selector transfer.
- L46 — // Потрібен успішний виклик і порожня відповідь або логічне true.
- L47 — // Закривається допоміжна функція; перевірка резервів тут не виконується.

`_safeTransfer` підтримує токени, які не повертають значення, але цей адаптер не доводить економічну коректність обміну. Підтвердження переказу і перевірка інваріанта мають різні завдання: перше перевіряє результат зовнішнього виклику, друга — отриману парою оплату.

### 1.2. Повний шлях swap

[UniswapV2Pair.sol, L159–L162](https://github.com/Uniswap/v2-core/blob/6a9e7c97860676e0992f22a49665760444c1cdf5/contracts/UniswapV2Pair.sol#L159-L162)
```solidity
    function swap(uint amount0Out, uint amount1Out, address to, bytes calldata data) external lock {
        require(amount0Out > 0 || amount1Out > 0, 'UniswapV2: INSUFFICIENT_OUTPUT_AMOUNT');
        (uint112 _reserve0, uint112 _reserve1,) = getReserves(); // gas savings
        require(amount0Out < _reserve0 && amount1Out < _reserve1, 'UniswapV2: INSUFFICIENT_LIQUIDITY');
```

- L159 — // Зовнішній swap приймає вихідні суми, одержувача й дані та використовує lock.
- L160 — // Принаймні один запитаний вихід повинен бути строго додатним.
- L161 — // Локально зберігаються резерви, які були зафіксовані перед обміном.
- L162 — // Кожен вихід має бути меншим за відповідний попередній резерв.

Вхідний параметр не містить довіреної суми оплати. Викликач задає вихід, а контракт визначає реальний вхід за балансами. Перед передачею коштів також перевіряється, що `to` не дорівнює адресі жодного токена; це не є загальною автентифікацією одержувача.

[UniswapV2Pair.sol, L170–L174](https://github.com/Uniswap/v2-core/blob/6a9e7c97860676e0992f22a49665760444c1cdf5/contracts/UniswapV2Pair.sol#L170-L174)
```solidity
        if (amount0Out > 0) _safeTransfer(_token0, to, amount0Out); // optimistically transfer tokens
        if (amount1Out > 0) _safeTransfer(_token1, to, amount1Out); // optimistically transfer tokens
        if (data.length > 0) IUniswapV2Callee(to).uniswapV2Call(msg.sender, amount0Out, amount1Out, data);
        balance0 = IERC20(_token0).balanceOf(address(this));
        balance1 = IERC20(_token1).balanceOf(address(this));
```

- L170 — // Перший токен відправляється оптимістично, до остаточної перевірки надходження оплати.
- L171 — // Другий токен також може бути переданий до завершення розрахунку.
- L172 — // За непорожніх даних callback викликається на to з адресою безпосереднього викликача swap.
- L173 — // Після повернення керування читається фактичний баланс першого токена пари.
- L174 — // Окремо читається фактичний баланс другого токена, включно з поверненою оплатою.

Якщо `data` порожні, виклик `uniswapV2Call` пропускається; оплата могла надійти раніше. За непорожніх даних одержувач може використати отримані активи, виконати інші операції та оплатити обмін перед поверненням. Саме така послідовність забезпечує flash swap. Адреса `to` і `msg.sender` можуть відрізнятися: callback отримує перша, а друга передається аргументом. Одержувач повинен сам перевірити справжність пари перед використанням власних коштів; lock пари такої перевірки не замінює.

[UniswapV2Pair.sol, L176–L178](https://github.com/Uniswap/v2-core/blob/6a9e7c97860676e0992f22a49665760444c1cdf5/contracts/UniswapV2Pair.sol#L176-L178)
```solidity
        uint amount0In = balance0 > _reserve0 - amount0Out ? balance0 - (_reserve0 - amount0Out) : 0;
        uint amount1In = balance1 > _reserve1 - amount1Out ? balance1 - (_reserve1 - amount1Out) : 0;

```

- L176 — // Вхід token0 визначається як перевищення балансу над резервом після віднімання виходу.
- L177 — // Для token1 застосовується та сама формула з незалежними сумами.
- L178 — // Обмін відхиляється, якщо жоден токен фактично не надійшов у розрахунок.

Формально `amountIn = max(balanceAfter − (reserveBefore − amountOut), 0)`. Надіслане раніше збільшення балансу також потрапить у цей розрахунок. Контракт перевіряє спостережуване надходження, а не довільне твердження callback про переказ.

У реалізації умова допускає більший добуток, тому звичайне твердження «після swap добуток завжди дорівнює попередньому» неточне. Комісія залишається в балансах і може збільшувати їхній нескоригований добуток. Перевірка охоплює обидва баланси, обидва виходи та фактичні входи.

## 2. V3: концентрована ліквідність і оплата після зміни стану

### 2.1. Ціна, ticks і активна ліквідність

У V3 ціна визначає, які позиції беруть участь в обміні. Позиція має межі `tickLower` та `tickUpper`; ліквідність активна всередині відповідного діапазону. При переході через ініціалізований tick сума ліквідності наступного кроку може змінитися відповідно до `liquidityNet`. Звідси випливає необхідність аналізувати послідовність кроків, переходи між ticks і округлення, а не переносити перевірку добутку глобальних балансів із V2. [Обчислення внесків позиції](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/UniswapV3Pool.sol#L327-L370) розрізняє ціну нижче, всередині та вище діапазону.

[IUniswapV3PoolState.sol, L46–L48](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/interfaces/pool/IUniswapV3PoolState.sol#L46-L48)
```solidity
    /// @notice The currently in range liquidity available to the pool
    /// @dev This value has no relationship to the total liquidity across all ticks
    function liquidity() external view returns (uint128);
```

- L46 — // Опис getter прямо визначає ліквідність як доступну в поточному діапазоні.
- L47 — // Значення не слід ототожнювати із сумарною ліквідністю всіх позицій.
- L48 — // Інтерфейс повертає поточну активну ліквідність як беззнакове число uint128.

[TickMath](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/libraries/TickMath.sol#L4-L23) пов’язує tick із ціною через основу `1.0001`. Значення `sqrtPriceX96` має формат Q64.96: квадратний корінь сирого відношення token1/token0 помножено на `2^96`. Тому сира ціна обчислюється як `Praw = (sqrtPriceX96 / 2^96)^2`. Для ціни у звичних одиницях token1 за один token0 застосовується `Phuman = Praw × 10^(decimals0 − decimals1)`. Наприклад, різні decimals змінюють масштаб навіть за того самого числового `sqrtPriceX96`. Ці формули пояснюють формат; точна програмна реалізація має уникати переповнення при піднесенні до квадрата й враховувати округлення.

Межі сітки мають ціни `P(i)=1.0001^i`. Усередині ділянки зі сталою активною ліквідністю віртуальні резерви задовольняють `xᵥ=L/√P`, `yᵥ=L√P`, отже `xᵥ·yᵥ=L²`. Для зростання сирої ціни від `Pₐ` до `Pᵦ` обсяги без комісії становлять `amount0Out=L(1/√Pₐ−1/√Pᵦ)` і `amount1In=L(√Pᵦ−√Pₐ)`. Віртуальні резерви не дорівнюють загальним ERC-20 балансам контракту. Квадратний корінь ціни дає зручні вирази для цих дельт; перетин межі потребує наступного кроку з оновленою L. Реалізація [SqrtPriceMath](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/libraries/SqrtPriceMath.sol#L145-L194) доповнює модель масштабуванням і спрямованим округленням.

[UniswapV3Pool.sol, L720–L724](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/UniswapV3Pool.sol#L720-L724)
```solidity

                    state.liquidity = LiquidityMath.addDelta(state.liquidity, liquidityNet);
```

- L722 — // До активної ліквідності додається підписана зміна перетнутого tick.

- L745 — // Другому полю присвоюється tick після проходження всіх кроків обміну.

Важлива властивість: цей запис виконується **до платіжного callback**, що видно з [порядку рядків 732–787](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/UniswapV3Pool.sol#L732-L787). Під час callback читач може бачити вже нову ціну, хоча вхідний токен ще не сплачено. Це спростовує пояснення, ніби пул спочатку повністю отримує оплату, а вже потім змінює ціну. Захищені повторні операції заблоковані, але доступність читання не означає остаточність розрахунку для зовнішньої системи.

### 2.3. Callback викликача і симетричні перевірки оплати

Знак повернених `amount0` та `amount1` задає напрям зобов’язання: додатна сума має надійти пулу, від’ємна відповідає виданому токену. Одержувач виходу задається `recipient`, тоді як callback виконується на `msg.sender`. У напрямі `zeroForOne` вихід token1 передається перед фіксацією балансу вхідного token0.

[UniswapV3Pool.sol, L775–L779](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/UniswapV3Pool.sol#L775-L779)
```solidity
            uint256 balance0Before = balance0();
            IUniswapV3SwapCallback(msg.sender).uniswapV3SwapCallback(amount0, amount1, data);
            require(balance0Before.add(uint256(amount0)) <= balance0(), 'IIA');
        } else {
            if (amount0 < 0) TransferHelper.safeTransfer(token0, recipient, uint256(-amount0));
```

- L775 — // Фіксується баланс вхідного token0 безпосередньо перед платіжним callback.
- L776 — // Callback викликається на початковому викликачі swap із підписаними сумами.
- L777 — // Баланс token0 після callback повинен зрости щонайменше на належну суму.
- L778 — // Починається симетрична гілка обміну token1 на token0.
- L779 — // Від’ємна сума token0 перетворюється на вихідний переказ одержувачу.

[UniswapV3Pool.sol, L781–L784](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/UniswapV3Pool.sol#L781-L784)
```solidity
            uint256 balance1Before = balance1();
            IUniswapV3SwapCallback(msg.sender).uniswapV3SwapCallback(amount0, amount1, data);
            require(balance1Before.add(uint256(amount1)) <= balance1(), 'IIA');
        }
```

- L781 — // Для протилежного напряму фіксується початковий баланс вхідного token1.
- L782 — // Той самий інтерфейс callback викликається на msg.sender, а не recipient.
- L783 — // Баланс token1 має покрити попередній баланс і обчислену оплату.
- L784 — // Закривається друга гілка перевірки надходження вхідного токена.

Ці перевірки є порівняннями приросту відповідного балансу, а не перевіркою дозволу ERC-20 або поверненого callback значення. Попередній переказ до вимірювання `balanceBefore` не замінює потрібного приросту під час callback. Після перевірки генерується подія, а [рядок 787](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/UniswapV3Pool.sol#L786-L788) відновлює `slot0.unlocked`.

Реалізація callback повинна автентифікувати пул. Це прямо зазначено в [IUniswapV3SwapCallback](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/interfaces/callback/IUniswapV3SwapCallback.sol#L7-L14): без перевірки походження сторонній викликач міг би імітувати запит оплати. Блокування захищає стан пулу, автентифікація захищає платника, а балансова умова підтверджує фактичне надходження. Жодна із цих трьох перевірок не замінює інші.

### 2.4. Flash та oracle

Окрема функція `flash` використовує інший callback, що приймає комісії позики. Її не слід називати тим самим шляхом, що й `swap`.

```solidity

        if (amount1 > 0) TransferHelper.safeTransfer(token1, recipient, amount1);

        IUniswapV3FlashCallback(msg.sender).uniswapV3FlashCallback(fee0, fee1, data);
```

- L805 — // За ненульової суми token0 видається одержувачу flash-позики.
- L806 — // За ненульової суми token1 також видається одержувачу позики.
- L807 — // Порожній рядок відділяє передачу активів від виклику callback.
- L808 — // Flash-callback викликача отримує комісії обох токенів і довільні дані.
- L809 — // Порожній рядок відокремлює callback від подальшого вимірювання балансів.

[Перевірки flash](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/UniswapV3Pool.sol#L791-L818) порівнюють кінцеві баланси з балансами до видачі плюс комісії. Отже, потрібне повернення основної суми й комісії для кожного токена. На відміну від ручного блокування `swap`, `flash` використовує модифікатор `lock`.

У V2 акумулятори інтегрують відношення резервів за часом: різниця двох значень, поділена на тривалість, дає арифметичну середню ціну з часовими вагами. V3 накопичує tick, тобто логарифмічне представлення ціни.

[Oracle.sol, L39–L43](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/libraries/Oracle.sol#L39-L43)
```solidity
                blockTimestamp: blockTimestamp,
                tickCumulative: last.tickCumulative + int56(tick) * delta,
                secondsPerLiquidityCumulativeX128: last.secondsPerLiquidityCumulativeX128 +
                    ((uint160(delta) << 128) / (liquidity > 0 ? liquidity : 1)),
                initialized: true
```

- L39 — // Нове спостереження зберігає часову позначку моменту обчислення акумуляторів.
- L40 — // До накопиченого tick додається його поточне значення, помножене на час.
- L41 — // Починається оновлення акумулятора секунд на одиницю активної ліквідності.
- L42 — // Час масштабується на Q128 і ділиться на ліквідність або одиницю.
- L43 — // Спостереження позначається ініціалізованим і придатним для подальшого читання.

Середній tick дорівнює різниці `tickCumulative`, поділеній на часовий інтервал. Перетворення через `1.0001^averageTick` відповідає геометричному часовому усередненню ціни, з урахуванням дискретизації ticks та округлень. Називати це арифметичним середнім цін некоректно. Oracle зберігає кільцевий масив спостережень; [write](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/libraries/Oracle.sol#L78-L102) не створює другий запис за тієї самої часової позначки, а [observeSingle](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/libraries/Oracle.sol#L245-L287) обробляє часові запити. Довший інтервал потребує достатньої історії; сам факт наявності oracle не гарантує стійкої зовнішньої оцінки.

## 3. V4: singleton та розрахунок у межах unlock

### 3.1. Спільний менеджер і межа сесії

У V4 стани пулів розміщено в одному `PoolManager`, у [mapping _pools](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/PoolManager.sol#L78-L99). Пул ідентифікується структурою [PoolKey](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/types/PoolKey.sol#L10-L22), яка містить дві валюти, комісію, крок ticks та адресу hooks. Це відрізняється від зберігання активів кожним окремим контрактом пари чи пулу. Внутрішня зміна стану пулу може створювати зобов’язання, не виконуючи негайного зовнішнього переказу на кожному кроці маршруту.

Зазвичай менеджер заблокований. Зовнішній виклик `unlock` перевіряє відсутність уже відкритої сесії та дозволяє операції через `Lock.unlock()`. Потім викликач отримує керування для виконання послідовності дій.

[PoolManager.sol, L109–L113](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/PoolManager.sol#L109-L113)
```solidity
        // the caller does everything in this callback, including paying what they owe via calls to settle
        result = IUnlockCallback(msg.sender).unlockCallback(data);

        if (NonzeroDeltaCount.read() != 0) CurrencyNotSettled.selector.revertWith();
        Lock.lock();
```

- L109 — // Коментар визначає callback як місце виконання дій і погашення боргів.
- L110 — // Менеджер викликає unlockCallback на безпосередньому викликачі функції unlock.
- L111 — // Порожній рядок розділяє виконання користувацької послідовності та остаточну перевірку.
- L112 — // Наявність хоча б одного незакритого облікового запису спричиняє revert.
- L113 — // Після успішної перевірки менеджер повертається до заблокованого стану.

Тут «розблоковано» означає дозвіл складеної операції. [onlyWhenUnlocked](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/PoolManager.sol#L95-L114) пропускає відповідні методи лише всередині сесії; повторний `unlock` відхиляється. Це не глобальна заборона всіх вкладених викликів менеджера. Інші контракти, зокрема hooks, можуть виконувати дозволені дії в межах відкритого розрахунку, тому інтеграція має враховувати вкладені взаємодії.

[Lock.sol, L17–L21](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/libraries/Lock.sol#L17-L21)
```solidity
    function lock() internal {
        assembly ("memory-safe") {
            tstore(IS_UNLOCKED_SLOT, false)
        }
    }
```

- L17 — // Внутрішня функція завершує доступ до операцій відкритої сесії.
- L18 — // Відкривається assembly-блок для запису у transient storage менеджера.
- L19 — // Прапорець розблокування встановлюється у false через операцію tstore.
- L20 — // Закривається assembly-блок після запису тимчасового прапорця.
- L21 — // Закривається функція lock, яка не використовує постійний storage.

Стан `Lock` зберігається через `tstore/tload`. За [EIP-1153](https://eips.ethereum.org/EIPS/eip-1153) transient storage доступне між викликами одного контракту в межах транзакції, а наприкінці транзакції очищується; відкочування також скасовує відповідні записи. Саме очищення не є перевіркою платежу: незакритий борг має спричинити помилку до успішного повернення `unlock`.

### 3.2. Окремий облік кожної адреси та валюти

[CurrencyDelta](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/libraries/CurrencyDelta.sol#L6-L42) реалізує тимчасовий аналог відображення. Ключ залежить одночасно від адреси учасника і валюти.

Аналогічно, невибраний позитивний залишок потребує закриття; перевірка охоплює і борги, і вимоги учасників.

- L361 — // Позначка синхронізованої валюти скидається після вимірювання платежу.
- L362 — // Закривається гілка оброблення платежу за допомогою ERC-20.

[_settle](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/PoolManager.sol#L348-L365) додає отриману суму до дельти одержувача зарахування. Для нативної валюти сумою платежу є `msg.value`; для синхронізованого ERC-20 ненульовий `msg.value` відхиляється. `settle()` зараховує оплату викликачу, а `settleFor(recipient)` — заданій адресі. Знімок синхронізації є спільним станом менеджера, тому послідовність викликів між знімком і погашенням має значення.

[PoolManager.sol, L291–L295](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/PoolManager.sol#L291-L295)
```solidity
    function take(Currency currency, address to, uint256 amount) external onlyWhenUnlocked {
        unchecked {
            // negation must be safe as amount is not negative
            _accountDelta(currency, -(amount.toInt128()), msg.sender);
            currency.transfer(to, amount);
```

- L291 — // Функція take доступна лише під час відкритої сесії менеджера.
- L292 — // Відкривається блок unchecked для безпечного заперечення перевіреної суми.
- L293 — // Коментар пояснює передумову: вхідна сума не може бути від’ємною.
- L294 — // Дельта викликача зменшується на суму запитаного отримання валюти.
- L295 — // Після облікової зміни валюта фактично передається зазначеному одержувачу.

`take` не вимагає позитивної дельти на момент виклику: отримання може створити тимчасовий борг, який слід закрити до повернення callback. Це демонструє відмінність між локально дозволеним проміжним станом і глобальною умовою завершення сесії. Простий успіх `take` або `swap` усередині callback ще не означає успіх зовнішнього `unlock`.

### 3.4. Hooks і причини зміни газових витрат

`IHooks` описує точки розширення перед і після ініціалізації, зміни ліквідності, обміну та пожертви. [Hooks](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/libraries/Hooks.sol#L15-L45) вибирає дозволені виклики за прапорцями в молодших бітах адреси. Тому наявність методу в інтерфейсі ще не означає, що кожен пул викличе його.

[IHooks.sol, L103–L105](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/interfaces/IHooks.sol#L103-L105)
```solidity
    function beforeSwap(address sender, PoolKey calldata key, SwapParams calldata params, bytes calldata hookData)
        external
        returns (bytes4, BeforeSwapDelta, uint24);
```

- L103 — // Перед обміном hook отримує викликача, ключ пулу, параметри й додаткові дані.
- L104 — // Метод є зовнішньою точкою передачі керування контракту розширення.
- L105 — // Повертаються selector, дельта hook та можливе перевизначення комісії пулу.

[beforeSwap](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/libraries/Hooks.sol#L247-L282) може за дозволених прапорців змінювати суму, що надходить до алгоритму пулу; для динамічної комісії передбачено перевизначення ставки. Перевіряється, зокрема, щоб дельта не перевела операцію між типами exact input та exact output. [afterSwap](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/libraries/Hooks.sol#L284-L315) бачить результат і може вплинути на підсумкові облікові дельти за відповідного дозволу.

[PoolManager.sol, L220–L224](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/PoolManager.sol#L220-L224)
```solidity
        BalanceDelta hookDelta;
        (swapDelta, hookDelta) = key.hooks.afterSwap(key, params, swapDelta, hookData, beforeSwapDelta);

        // if the hook doesn't have the flag to be able to return deltas, hookDelta will always be 0
        if (hookDelta != BalanceDeltaLibrary.ZERO_DELTA) _accountPoolBalanceDelta(key, hookDelta, address(key.hooks));
```

- L220 — // Оголошується окрема дельта, яка належатиме контракту hook.
- L221 — // Бібліотека Hooks після оброблення зовнішнього hook повертає скоригований результат викликача та дельту hook.
- L222 — // Порожній рядок відділяє виклик розширення від обліку його результату.
- L223 — // Коментар пояснює нульовий результат за відсутності дозволу повертати дельти.
- L224 — // Ненульова дельта hook обліковується саме за адресою контракту розширення.

Наступний рядок обліку [226](https://github.com/Uniswap/v4-core/blob/bea7f6d1c11cd5dc4f0d5151ffa37a1c239feee6/src/PoolManager.sol#L220-L227) записує дельту викликача. Отже, додаткові можливості розширення не усувають загальну вимогу закрити кожен запис. Перевірка selector відповіді і дозволів на дельти також не доводить коректності власної логіки hook: його доступ, зовнішні виклики та інваріанти потребують окремого огляду.

Потенційна економія газу випливає з трьох механізмів: спільного менеджера замість окремого контракту для кожного пулу, взаємного погашення проміжних дельт без обов’язкових зовнішніх переказів на кожному кроці та тимчасового сховища для розрахунку. Це пояснює напрям оптимізації, але не визначає універсального відсотка. Кількість переходів між ticks, ERC-20 виклики, hooks і форма маршруту змінюють фактичні витрати; кількісне порівняння потребує однакових сценаріїв і вимірювань.

## 4. Порівняння та технічні висновки

| Критерій | V2 | V3 | V4 |
|---|---|---|---|
| Розміщення стану | Окремий контракт пари з резервами | Окремий пул із ціною, ticks і позиціями | Спільний менеджер, пули в mapping |
| Основний callback | Необов’язковий `uniswapV2Call` | Платіжний `uniswapV3SwapCallback` | `unlockCallback` для складеної сесії |
| Адресат callback | Одержувач `to` | Викликач `msg.sender` | Викликач `unlock` |
| Стан до оплати | Виходи передано, резерви ще попередні | Ціну й обліковий стан уже записано | Операції накопичують адресні валютні дельти |
| Остаточна перевірка | Інваріант зі скоригованими балансами | Приріст балансу потрібного вхідного токена | Кількість ненульових дельт дорівнює нулю |
| Режим блокування | Модифікатор `lock` на операціях пари | Ручне блокування `swap`; модифікатор для `flash` | Дозвіл операцій усередині `unlock` |
| Облік ліквідності | Резерви повного діапазону | Ліквідність активних діапазонів | Пули з діапазонами та розширеннями hooks |
| Усереднення ціни | Акумулятори арифметичного часового середнього | Акумулятор tick для геометричного середнього | Розглянуті фрагменти не встановлюють універсального oracle |

Усі три версії допускають проміжні стани, які не можна трактувати як остаточний розрахунок. V2 спочатку видає активи й згодом узгоджує резерви; V3 спочатку обчислює та записує нову ціну, а потім перевіряє оплату; V4 переносить межу перевірки на завершення сесії з потенційно багатьма діями. Тому розміщення зовнішнього виклику потрібно аналізувати разом із фінальною перевіркою та режимом повторного входу.

Помилка остаточної перевірки відкочує зміни в піддереві невдалого виклику, включно зі змінами вкладених викликів, переказами та журналами в цьому піддереві. Зовнішній викликач може перехопити помилку через підтримуваний механізм оброблення або низькорівневий виклик і продовжити свою транзакцію. Тому формулювання «кожен revert обов’язково скасовує всю зовнішню транзакцію» надто сильне. Ця межа відповідає [семантиці винятків Solidity](https://docs.soliditylang.org/en/latest/control-structures.html#error-handling-assert-require-revert-and-exceptions).

Для огляду інтеграції потрібні три незалежні відповіді: хто має право ініціювати callback; які зміни дозволені під час переданого керування; чим підтверджується остаточний платіж. Перевірка адреси захищає кошти інтегратора від підробленого callback. Блокування обмежує небезпечні переходи стану. Перевірка балансів або дельт підтверджує економічне завершення. Наявність одного механізму не є доказом двох інших.

Головна архітектурна зміна полягає у масштабі облікової операції: від резервів однієї пари через стан концентрованого пулу до адресних зобов’язань спільного менеджера. Це збільшує можливості композиції, але також змінює предмет перевірки. Для V2 вирішальною є правильність остаточних балансів; для V3 — послідовність переходів ціни, активної ліквідності й оплати; для V4 — закриття кожної пари адреса–валюта після всіх дозволених вкладених дій.
