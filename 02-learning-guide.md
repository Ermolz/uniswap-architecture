# Навчальний маршрут: callbacks і узгодженість стану Uniswap V2, V3 та V4

Головна думка: **токени можуть перейти до одержувача раніше, ніж контракт перевірить оплату. Якщо перевірка не проходить, зміни невдалого виклику скасовуються.** Щоб зрозуміти код, щоразу запитуємо: хто зараз виконується, що вже змінилося, що ще треба сплатити і що перевірять наприкінці?

Цей посібник пояснює механізм. Точні рядки коду й докази зібрано в [технічному звіті](01-technical-report.md#comparison) на зафіксованих версіях контрактів. Для швидкої підготовки до слайдів є [короткі нотатки](07-personal-notes.md).

## Маршрут читання

| Крок | Питання, на яке шукаємо відповідь |
|---|---|
| Основи нижче | Як один контракт викликає інший і що скасовує помилка? |
| V2 | Як видати токени й потім перевірити оплату за балансами? |
| V3 | Як діапазони ліквідності визначають результат обміну? |
| V4 | Як провести кілька операцій і розрахуватися наприкінці? |
| TWAP | Чому дві «середні ціни» можуть дати різні числа? |

Спочатку достатньо вміти переказати кожен механізм кількома реченнями. Формули та деталі точності варто пройти другим читанням.

## Мінімум Solidity для читання протоколу

**Контракт** — програма з адресою, функціями й збереженими даними. Ці дані називають **станом**. Solidity — мова контрактів; EVM — середовище, яке виконує їхні інструкції. **Пул** зберігає та обліковує активи для обміну; у V2 пул двох токенів також називають **парою**. **Своп** (`swap`) означає обмін.

Терміни, які зустрінуться в коді:

| Запис | Як читати |
|---|---|
| `uint256` / `int256` | Ціле число без знака / зі знаком |
| `address`, `bool` | Адреса; значення «так» або «ні» |
| `mapping`, `struct` | Значення за ключем; група пов’язаних полів |
| `bytes` | Дані, наприклад параметри для наступного виклику |
| `require(умова)` | Продовжити лише тоді, коли умова істинна |
| Модифікатор і `_` | Перевірки або дії навколо функції; `_` — місце виконання її тіла |
| `external`, `public` | Доступність функції для зовнішнього виклику; `public` для змінної створює функцію читання |
| `view` | Виклик може читати стан, але не змінювати його |

`view` не обіцяє, що прочитані дані вже остаточні: інший контракт може читати їх посеред операції. Докладніше — [основи Solidity](https://docs.soliditylang.org/en/latest/introduction-to-smart-contracts.html).

### Чия адреса міститься в `msg.sender`

`msg.sender` — адреса того, хто зробив **поточний** виклик. Вона змінюється з переходом до іншого контракту. Router, або маршрутизатор, організовує обмін; Pool — контракт пулу.

Уявімо звичайний ланцюжок: користувач → Router → Pool → Router.callback → Token.transfer.

| Де виконується код | Хто там є `msg.sender` |
|---|---|
| Початкова функція Router | Користувач |
| Функція Pool | Router |
| Callback у Router | Pool |
| `Token.transfer`, викликаний Router | Router |

Аргумент із назвою `sender` — лише передані дані. Наприклад, V2 передає адресу ініціатора `swap` у такому аргументі, але сам callback викликає пара. Тому для перевірки джерела callback потрібна адреса справжнього пулу, а не довільний аргумент чи `tx.origin` — адреса початкового відправника транзакції.

Таблиця описує звичайний виклик `CALL`. Спеціальний `DELEGATECALL` працює в іншому контексті; його тут не розглядаємо. [Глобальні змінні Solidity](https://docs.soliditylang.org/en/latest/units-and-global-variables.html#block-and-transaction-properties).

### Зовнішній `CALL` і callback

Зовнішній виклик тимчасово передає керування іншому контракту. Коли той успішно завершується, перший контракт продовжує роботу. Усе відбувається в межах тієї самої транзакції.

**Callback**, або зворотний виклик, — функція, яку протокол викликає у визначений момент. Наприклад: «Ось токени; тепер виконай потрібні дії й забезпеч оплату». Це не окреме завдання на потім. Контракт, що реалізує callback, має перевіряти, хто його викликав: сама назва функції не доводить довіру.

Зовнішній код може викликати ще один контракт або спробувати знову увійти до першого. Такий повторний вхід називають **reentrancy**. Блокування може обмежувати його, але саме по собі не доводить оплату. `STATICCALL` — окремий спосіб зовнішнього виклику, що забороняє зміни стану. [Зовнішні виклики Solidity](https://docs.soliditylang.org/en/latest/control-structures.html#external-function-calls).

### Три місця зберігання даних

| Місце | Просте пояснення | Що пам’ятати |
|---|---|---|
| `memory` | Тимчасові дані поточного виконання | Не є спільною пам’яттю всіх контрактів; внутрішні виклики можуть використовувати її |
| `storage` | Дані контракту, які зберігаються між транзакціями | Запис уже можна прочитати у вкладеному виклику, але помилка ще може його скасувати |
| `transient storage` | Тимчасові дані контракту на одну транзакцію | Доступні різним викликам цього контракту; очищуються наприкінці транзакції |

У V4 третій варіант зручний для обліку поточних зобов’язань. Його записи також скасовуються при відкаті. **Автоматичне очищення даних не є оплатою боргу.** [EIP-1153](https://eips.ethereum.org/EIPS/eip-1153).

### Межі `revert`

`revert` — відкат невдалого виклику: його зміни стану та зміни вкладених викликів скасовуються. Це охоплює перекази токенів і записи подій усередині цієї частини виконання.

Уявімо Router → Pool → Token. Якщо виклик Pool відкочується, його вкладені перекази Token теж скасовуються. Router може перехопити помилку через `try/catch` або перевірити результат низькорівневого виклику й продовжити роботу. Тоді незалежні зміни Router поза невдалим викликом можуть зберегтися. Якщо ж помилка доходить до верхнього рівня, відкочуються зміни всього виконання транзакції. Витрачений газ — оплата виконаних обчислень — через це не повертається. [Обробка помилок Solidity](https://docs.soliditylang.org/en/latest/control-structures.html#error-handling-assert-require-revert-and-exceptions).

## V2: спочатку видача, потім доказ оплати

**Простими словами:** пара видає токени, а потім перевіряє, чи достатньо отримала натомість.

Послідовність у `swap`:

1. Запам’ятати старі резерви й переказати вихідні токени.
2. Якщо `data` непорожні, викликати `uniswapV2Call` на адресі одержувача `to`.
3. Прочитати фактичні баланси та визначити, скільки токенів надійшло.
4. Перевірити добуток балансів із поправкою на комісію.
5. Лише після успіху оновити резерви.

**Баланс** — скільки токенів зараз обліковує токенний контракт за адресою пари. **Резерв** — останнє збережене парою значення для її обчислень. Під час callback баланс уже може змінитися, а резерв ще лишатися старим. Прямий переказ у пару також не оновлює резерв автоматично.

**Інваріант** — умова, яку успішна операція має зберегти. Знайома формула `x × y` допомагає зрозуміти V2, але перевірка оплати враховує ще й комісію 0,3% від входу:

```text
amountIn = max(balanceAfter − (reserveBefore − amountOut), 0)
balanceAdjusted = 1000 × balanceAfter − 3 × amountIn
balance0Adjusted × balance1Adjusted ≥ 1000² × reserve0 × reserve1
```

Перший рядок знаходить надходження понад баланс, який залишився б після видачі. Другий віднімає комісійну поправку. Третій порівнює скоригований добуток зі старими резервами. Самого зростання звичайного добутку балансів може бути недостатньо.

Блокування захищає від повторного входу в захищені функції **цієї пари**. Оплату перевіряє інваріант. Недоплата спричиняє відкат `swap` і його вкладених дій.

**Перевір себе:** чому вже видані токени не можна зберегти після невдалої перевірки? Звір відповідь із [розбором V2](01-technical-report.md#v2), а числа — зі [сценарієм V2](04-defense-preparation.md#scenario-v2).

## V3: ціна, діапазони та оплата розрахованого результату

**Простими словами:** постачальник ліквідності обирає, у якому діапазоні ціни його кошти беруть участь в обміні. Активна ліквідність — параметр тих позицій, які працюють за поточної ціни.

Тому загальний баланс V3 не дає ціну простим діленням двох балансів. Він може містити токени неактивних позицій і накопичені комісії. Для обміну потрібні ціна, активна ліквідність, межі діапазонів і правила комісії. [Концентрована ліквідність](https://developers.uniswap.org/docs/get-started/concepts/liquidity-providers/concentrated-liquidity).

### Як прочитати `sqrtPriceX96`

Назва кодує спосіб зберігання ціни: **квадратний корінь із ціни, помножений на `2^96`**. Такий масштаб дає змогу працювати з дробами через цілі числа.

Нехай `q = sqrtPriceX96`, а `Praw` — кількість мінімальних одиниць token1 за одну мінімальну одиницю token0. Тоді приблизно:

```text
sqrt(Praw) ≈ q / 2^96
Praw ≈ (q / 2^96)^2
Phuman = Praw × 10^(d0 − d1)
```

`d0` і `d1` — `decimals`, кількість десяткових знаків токенів. Останній рядок переводить співвідношення мінімальних одиниць у ціну цілих токенів.

Наприклад, `q = 2 × 2^96` означає `Praw = 4`, бо після ділення треба ще піднести результат до квадрата. За однакових `decimals` це 4 token1 за 1 token0. Якщо `d0 = 6`, а `d1 = 18`, ціна дорівнює `4 × 10^-12` token1 за 1 token0. Це умовний приклад, не ринкова ціна.

Реальні розрахунки платежу враховують точне цілочислове округлення; цих формул для них недостатньо. [Пояснення математики V3](https://blog.uniswap.org/uniswap-v3-math-primer).

### Як прочитати tick і активну ліквідність

**Tick** — номер цінової межі. Межі з номером `i` відповідає ціна `P(i) = 1.0001^i`: tick 0 дає 1, tick 1 — 1.0001. Так утворюється дискретна сітка цін.

Позиції можуть перекриватися. Припустімо, A має ліквідність 1000 у `[-60, 60)`, а B — 500 у `[0, 120)`. Ліва межа входить у діапазон, права — ні.

| Поточний збережений tick | Активні позиції | Активна ліквідність |
|---|---|---:|
| −1 | A | 1000 |
| 0 | A та B | 1500 |
| 60 | B | 500 |
| 120 | Немає | 0 |

Під час обміну ціна рухається кроками до наступної межі або заданого ліміту. На ініціалізованому tick — межі із записаними даними ліквідності — контракт застосовує `liquidityNet`, тобто її чисту зміну з урахуванням напряму руху.

Для точності: `tickSpacing` обмежує допустимі межі позицій; для прикладу вище підходить 60. Він не обмежує поточний tick лише кратними 60. На точній межі напрям перетину теж важливий: при русі до нижчої ціни код може зберегти `tickNext − 1`. [Перетин tick у коді V3](https://github.com/Uniswap/v3-core/blob/5ea68a77cb541c6b3812df783be71ba8c081e25f/contracts/UniswapV3Pool.sol#L720-L728).

### Що відбувається до callback

Послідовність V3: **обчислити обмін → записати результат у стан → видати токени → викликати callback → перевірити оплату**.

`uniswapV3SwapCallback` отримує викликач `swap`, а вихідні токени — адреса `recipient`. Ці адреси можуть відрізнятися. Додатний параметр callback означає суму, належну пулу; від’ємний — видану пулом.

Після callback баланс вхідного токена має зрости щонайменше на обчислену суму. Якщо оплати бракує, відкочуються й попередні записи ціни, ліквідності та вкладені перекази. Запис у стан до callback ще не є остаточним підтвердженням.

Для точності: `swap` керує блокуванням через `slot0.unlocked`, а окрема функція `flash` має інший callback — `uniswapV3FlashCallback` — для повернення позичених сум із комісією. Це різні операції.

**Перевір себе:** чому великий баланс пулу не доводить велику активну ліквідність? Чому ціну можна записати до оплати? Допоможуть [розбір V3](01-technical-report.md#v3) та [сценарій V3](04-defense-preparation.md#scenario-v3).

## V4: сесія операцій із кінцевим нульовим залишком зобов'язань

**Простими словами:** кілька обмінів можна виконати зі спільним обліком, а залишки розрахувати наприкінці.

**Singleton** означає, що стан багатьох пулів міститься в одному контракті `PoolManager`. Контракт-організатор викликає `unlock`; менеджер відкриває сесію й викликає на ньому `unlockCallback`. У callback можна виконати кілька операцій. Повторний `unlock` під час уже відкритої сесії відхиляється.

**Flash accounting** — облік тимчасових зобов’язань протягом цієї сесії. Кожна **дельта** показує залишок розрахунків для конкретної пари «адреса, валюта»:

- додатна дельта: менеджер винен цій адресі;
- від’ємна: ця адреса винна менеджеру;
- нульова: для цього запису розрахунок закрито.

Для тієї самої адреси `+20 B` та `−20 B` дають нуль. Борги різних адрес або валют так погашати не можна. Баланс менеджера спільний; він не є окремим резервом кожного пулу.

Для звичайного ERC-20, тобто токена зі стандартним інтерфейсом, типовий розрахунок боргу має такий порядок:

1. `sync(currency)` — запам’ятати баланс перед оплатою.
2. Переказати токени менеджеру.
3. `settle()` — зарахувати фактичний приріст балансу.

Якщо виконати `sync` після переказу, цей переказ уже входить у початковий баланс і не рахується новою оплатою. Для нативної валюти мережі розрахунок використовує `msg.value`, тобто суму, передану з викликом; порядок ERC-20 не переноситься буквально.

`take` переказує токени назовні й зменшує дельту викликача. Із `+30` отримання 30 дає нуль. Із нульової дельти та сама дія створює борг `−30`, який теж треба погасити.

Після повернення з callback менеджер перевіряє `NonzeroDeltaCount` — лічильник ненульових записів. **Має бути нуль для кожної пари «адреса, валюта»**, зокрема для всіх залучених адрес. Незакритий кредит теж перешкоджає успішному завершенню. Саме ця перевірка закриває розрахунок; очищення `transient storage` її не замінює.

**Hooks** — окремі контракти з додатковою логікою у дозволених точках, наприклад `beforeSwap` перед обміном або `afterSwap` після нього. Вони можуть впливати на операцію в межах своїх дозволів. Це не `unlockCallback`: він організовує всю сесію, тоді як hook працює в конкретній точці операції. Hooks не скасовують фінальну вимогу закрити дельти.

**Перевір себе:** що станеться, якщо сплатити борг, але залишити кредит `+1`? Відповідь і код — у [розборі V4](01-technical-report.md#v4), приклад — у [сценарії V4](04-defense-preparation.md#scenario-v4).

## TWAP: середня ціна і середній tick — різні обчислення

**Оракул** дає дані про ціну для інших контрактів. **TWAP** — середня ціна, зважена за часом: довший період має більшу вагу. Одного поточного значення ціни для цього недостатньо.

V2 накопичує «ціна × час». Різниця двох накопичених значень, поділена на час між ними, дає **арифметичну** середню. Якщо ціна 10 секунд дорівнювала 1, а наступні 10 секунд — 4:

```text
(1 × 10 + 4 × 10) / 20 = 2.5
```

V3 накопичує «tick × час». Tick відповідає логарифму ціни, тому перетворення середнього tick назад у ціну дає **геометричну** середню з поправкою на дискретизацію та округлення. Для того самого ідеалізованого прикладу:

```text
sqrt(1 × 4) = 2
```

Реальне значення V3 може трохи відрізнятися через цілі ticks. Для обох версій потрібні правильно обрані інтервал і напрям котирування. Наприклад, середня обернених цін не обов’язково дорівнює оберненій середній ціні. Доступна історія теж має значення; її докладно розібрано в [поглибленому матеріалі](06-deep-dive.md#oracle-history).

Наявність оракула V3 не означає такого самого вбудованого механізму у V4. Першоджерела: [оракул V2](https://developers.uniswap.org/docs/protocols/v2/concepts/oracles) і [whitepaper V3, розділ 5](https://uniswap.org/whitepaper-v3.pdf).

## Практична вправа: пояснити рядки власними словами

Відкрий по одному фрагменту V2, V3 і V4 у звіті. Для кожного познач п’ять місць: початковий стан, зовнішній виклик, запис стану, перевірка оплати, завершення блокування або сесії.

Пояснюй дію через причину й наслідок: «Контракт запам’ятовує баланс, щоб після callback виміряти оплату. Якщо приріст замалий, виклик відкочується». Це корисніше, ніж лише повторити назву функції.

Напиши власні навчальні коментарі й звір їх із повним кодом. Збережи посилання на відповідну версію Uniswap: пояснення до чужого коду не змінює авторство самого контракту.

Перед виступом спробуй без підглядання розрізнити:

- блокування повторного входу та перевірку оплати;
- баланс токена, резерв V2 та активну ліквідність V3;
- callback обміну, callback позики, `unlockCallback` і hook;
- відкат одного виклику з підвикликами та всієї транзакції.

Для перевірки є [питання до захисту](04-defense-preparation.md). Для точного розрахунку свопу V3, округлення комісії та часткового виконання — [поглиблений розбір](06-deep-dive.md).
